# 設計メモ（Technology Radar）

作成: 2026-10-18 / 更新: 2026-10-30。設計の判断とその理由・経緯を残す自分用のメモ。プロジェクトの概要は [README](../README.md) を見る。

## 目的
- 『ソフトウェアエンジニアリングの基礎 ~コーダーからエンジニアになるための実践ガイド~』（オライリー・ジャパン、ISBN 978-4-8144-0178-9）14章「キャリアマネジメント」14.1.1「自分の情熱を注げるものを見つける」の文脈で、**自分がワクワクする技術・仕事を探す**ためのアプリ
- エンジニア求人を取得 → 1件ずつ表示 → 自分の反応を記録 → 傾向を集計する
- 利用者は自分のみ
- きっかけ: 2026-10-16 カンファレンスで「無性に作りたい」気持ちになった

## 成功の形
1. 「この求人に関わりたい」「この技術に触れたい」と思えるものが見つかる
2. データから以下が言える
   - +1 の求人に共通する技術・分野・働き方（上位3つ程度）
   - -1 の理由に繰り返し出る「避けたい働き方」の特徴
   - 自分が思っている興味と、実際の反応のズレ

## ユーザーストーリー

### 目的の層（なぜ作るか）
- 好きな技術を語りたいとき、自分がどんな技術スタックに関心があるかを傾向から話せる
- 気持ちが落ち込んでいるとき、ワクワクする技術や仕事を見てモチベーションを上げられる
- ジョブローテーションのとき、興味のある技術・仕事をもとに自分に合うポジションを説明できる
- 振り返りのとき、興味関心をもとに、業務で力を発揮できた・楽しかった・つらかった理由を理解できる
- （保留）新しい技術を学ぶとき、求人の需要の高低から今学ぶべきか判断できる → 今は早いので対象外

### 操作の層（何ができるか）
- 入力: 求人カードを見て、+1 / -1 をボタン（理想はマッチングアプリのようなスワイプ）で付けられる。気になれば詳細を開ける。判断できなければスキップできる
- A. 傾向を言葉にする: 気になる求人の傾向をグラフや表で表示できる
- B. 元気を出す: +1 の求人をリストで表示できる
- D. 振り返る: 時期を絞り込んで、+1 を付けた求人を見られる

## 決定事項

### 求人の取得元
調査した全サイトの判定と根拠は [docs/job-sources.md](job-sources.md) にまとめてある。実装中に見返す決定事項だけの早見表は [docs/cheatsheet.md](cheatsheet.md)、後回しにしたものは [docs/todo.md](todo.md)。
**取得元は paiza の1つで始める**（2026-10-25 決定）。

| 取得元 | 方式 | 取得量 | 備考 |
|---|---|---|---|
| paiza（https://paiza.jp/career/job_offers） | HTML。`/sitemap.xml.gz` で一覧 → 詳細ページを取得 | **1日30件まで**、間隔5秒 | エンジニア求人のみ。robots.txtは全許可。規約第24条5号は「私的利用の範囲を超える利用」のみ禁止 |

- paizaを選んだ理由: エンジニア専門で、技術（開発言語・フレームワーク）と働き方（特徴）がラベルとして構造化されている。sitemapの全件に `lastmod` がある。給料が JSON-LD に数値で入っている
- 見送り: Green（エンジニア以外の求人が混ざる、技術の項目がない）、Greenhouse（確認した企業ではエンジニア系が82件中28件、給料・技術が構造化されていない）
- 2つ目の候補（後で決める）: 特定の企業を追うならGreenhouse / Lever、JS描画に対応するならForkwell Jobs、規約が確認できればJapan Dev
- **使わない（規約でスクレイピングを明示的に禁止）**: Findy（第13条。第16条で求人情報は「秘密情報」扱い）、Geekly（第15条⑾。第14条で求人情報は秘密保持の対象）、Offers、YOUTRUST、転職ドラフト、HERP Careers
- **使わない（その他）**: エン転職（robots.txtでClaudeBotを全面禁止）、ビズリーチ（会員制）、Wantedly（規約で事前承諾のないスクレイピングを禁止）
- **レバテック**: 保留。一覧 `/engineer/offer/search/` はrobots.txtでDisallow、詳細ページは許可、`sitemap.xml` あり。ClaudeBotは全面禁止。自動アクセスはCloudFrontで403になる
- 見送り: Remotive / We Work Remotely（海外求人は日本と条件が違いすぎて参考にならない）、求人メール（結局サイトを見に行く必要があり、スクレイピングは避けられない）
- ハローワーク求人情報APIは、対象が自治体・職業訓練施設・職業紹介事業者のため、個人では利用できない見込み
- 取得したデータは個人利用に限り、公開・共有しない
- 取得量を増やす目的は分析用（将来のストーリー5に備えてデータを貯める）

### スクレイピングのルール
- robots.txt と利用規約の両方で禁止されていないサイトの、ログイン不要な公開ページに限る
- 一覧はsitemapから取る（サイトが機械向けに公開している正規の入口）。詳細ページのパスがrobots.txtで許可されているかはサイトごとに確認する
- paizaのsitemap（gzipで431KB）から `/career/job_offers/{id}` のURLだけを使う（約2.2万件。`student/` や `en_try/` は対象外）。`<lastmod>` の新しい順に並べ、未取得のものだけ詳細を取る。sitemap自体の取得は1日1回まで
- HTMLの取得は1サイト1日30件まで、リクエスト間隔は5秒以上。実行は1日1回、自動（2026-10-30 に「手動実行」から変更。定期実行のため。量は変えないので取得元への負担は同じ）
- 取得済みURLは再取得しない
- User-Agentはブラウザを装わず、正直に名乗る（例: `technology-radar (personal use)`）。403などで弾かれたら回避しない

### データの持ち方
- **原文（生データ）**: 取得したものを元の形式のまま（HTML / JSON）DBの `raw_documents` に保存する。取得日時・取得元・URLも残す
- **構造化データ**: 集計に使う項目だけ `jobs` に持つ。抽出ルールを変えたら、原文から過去分を再抽出できるようにする
- 理由: 何を分析軸にすべきかまだ分からないため、後から抽出し直せるよう原文を残す
- 正規化（技術のテーブル化など）は、必要になったら原文から再抽出して行う
- 「抽出」は raw_documents → jobs の変換のこと
- 技術スタックと働き方は、paizaのラベルからそのまま取る（正規表現やAIでの抽出は不要）。将来、ラベルのない取得元を足すときは、評価済みの求人（数十〜数百件）にだけAIをかければコストが抑えられる

### paizaの詳細ページの形（実在のページ全体で確認、1ページ約65KB）
例の値は、構造をまねた架空の求人ページ（`spec/fixtures/files/fake/paiza_job_offer.html`）のもの。実在の求人の内容は公開しない。

| 項目 | ページ上の場所 | 例（架空） |
|---|---|---|
| 求人タイトル → `title` | `<h1>`（`<title>` はサイト名が付くので使わない） | 架空の求人タイトル【リモート可】Rails で社内ツールを作る |
| 職種名 → `position` | 「職種名」欄。JSON-LD の `title` もこれ | Webアプリケーションエンジニア |
| 職種 → `job_types` | 「職種」欄（「、」区切り） | バックエンド/サーバサイド、フロントエンド |
| ポジション（jobsには持たない） | 「ポジション」欄 | テックメンバー |
| 応募要件（jobsには持たない） | 「応募要件」欄、JSON-LD の `skills` | — |
| 会社 → `company` | `h2.a-heading-primary-large`（ページ上部と企業情報の2か所）、JSON-LD の `hiringOrganization` | 株式会社サンプル |
| 給料 → `salary_min` / `salary_max` | JSON-LD `JobPosting` の `baseSalary`（**円の数値**）。JSON-LD がない求人は「給与(想定年収)」欄の文字列 | minValue 5000000 / maxValue 8000000 → 500 / 800（万円） |
| 技術 → `technologies` | 「主要開発技術」「開発言語」「フレームワーク」のラベル（span）＋「クラウドプラットフォーム」「データベース」（「、」区切り） | Ruby, TypeScript, Ruby on Rails, Amazon Web Services, PostgreSQL |
| 特徴 → `features` | 「特徴」の見出しの下のラベル（span） | フルリモート, 副業OK, フレックス |
| 業務内容 → `description` | 「求人概要」欄（`#job-offer-summary`）の説明文 | 株式会社サンプルは、架空の会社です。… |

- 開発言語・フレームワーク・特徴はどれも同じCSSクラスなので、直前の見出しで区別する
- JSON-LD の `skills` は技術の一覧ではなく、応募要件の文章
- **`paiza_lib/paiza/` の20件はページ全体ではない**。`fetch_job_pages.rb` が `.o-recruiters-show` の部分だけを切り出して保存しているため、`<title>`・`<h1>`・JSON-LD がない。原文のフィクスチャには使えない

### 構成（Railsアプリの中で名前空間を分ける）
- 取得部分は `lib/scraper/`（`Scraper::`）に置き（2026-10-25 に `Ingestion` から改名。取得元がpaizaだけの今は「何をしているか」が一目でわかる名前を優先する。APIの取得元を足すときに名前を見直す）、rakeタスク（`scraper:fetch` / `scraper:reparse`）から動かす。デプロイ後はサーバーで、Solid Queue の定期ジョブ（`config/recurring.yml`）から1日1回動かす
- 画面側（controllers / views）は `Scraper::` を参照しない。モデル（RawDocument / Job / Reaction / Reason）は両方から使う
- リポジトリは分けない。DBを共有する以上、分けるとスキーマ・モデルの持ち主が2つになり、依存が見えなくなる（共有データベース）。必要になれば `lib/scraper/` を切り出せばよい
- `app/` ではなく `lib/` に置く理由: Zeitwerk では `app/` 直下のディレクトリがそれぞれ読み込みの起点になるため、`app/scraper/paiza_parser.rb` は `Scraper::PaizaParser` ではなく `PaizaParser` になる。Rails 8 の `config.autoload_lib` で `lib/scraper/paiza_parser.rb` は `Scraper::PaizaParser` として読み込まれる

```
rake jobs:fetch
 └ Scraper::Runner#call …………………… 全体の流れだけを持つ（Service Object）
     ├ PaizaFetcher#fetch_new(limit:, skip:) → [Payload(url, content_type, body)]
     │     └ PoliteHttpClient#get(url) …… 間隔・UA
     └ Payloadごとに:
         ├ RawDocument.create! ……………… 必ず保存
         └ ParseRawDocument#call(raw) …… 失敗しても次のPayloadへ進む
               └ PaizaParser#parse(body) → Hash（DBにもHTTPにも触れない）
                 → Job.create! または raw.update!(parse_error:)

rake jobs:reparse ……………………… 保存済みの原文に ParseRawDocument をかけ直す
```

| 設計判断 | 理由 |
|---|---|
| 取得元が1つのうちは、小さく最低限で始める | `PaizaFetcher` / `PaizaParser` を具体的なクラスとして作る。差し替える相手がいないのに共通インターフェースを先に決めると、2つ目の取得元が来たときに合わないことが多い |
| Strategyは2つ目の取得元を足すときに導入する | 2つの具体的なクラスの共通部分から、インターフェースを抜き出す |
| Fetcher と Parser は最初から分ける | 取得元の数に関係なく、再抽出に要るのはParserだけでHTTPは要らない。Parserは「原文 → Hash」の純粋な変換になり、フィクスチャだけでテストできる |
| `skip:` で取得済みURLを渡す | FetcherがDBを知らずに済む |
| HTTP部分は `PoliteHttpClient` のインスタンスを渡す（依存性の注入） | 「最後にリクエストした時刻」という状態を持たせるため、mixinにはしない。テストで偽物に差し替えられる |
| ActiveRecordのコールバック（`after_create` でparse）は使わない | コールバック内の例外で原文の保存ごとロールバックされ、「原文は必ず保存」に反する |
| 継承（Template Method）・Factoryは使わない | 取得元が1つの段階では過剰 |

### 失敗の扱い
| 失敗 | 何が起きたか | 扱い |
|---|---|---|
| 取得の失敗 | HTTPエラー・タイムアウト | 何も保存しない。URLは未取得のまま残り、次回自然に取り直される |
| 原文の保存失敗 | DBエラー | 記録する先がないので例外としてログに出す |
| parseの失敗 | 原文は保存できたが、jobsに変換できない（必須項目がない、ページの構造が変わった等） | `raw_documents.parse_error` に記録し、次の原文へ進む。再抽出に成功したらNULLに戻す |

### 取得部分（PoliteHttpClient / PaizaFetcher）の設計（2026-10-30）

```ruby
client  = Scraper::PoliteHttpClient.new(user_agent: "technology-radar (personal use)", interval: 5)
client.get(url)   # → 本文（String）。200以外は例外。3xx も例外（追わない）。403 / 429 は「拒否された」専用の例外

fetcher = Scraper::PaizaFetcher.new(client: client)
fetcher.fetch_new(limit: 30, skip: ->(url) { RawDocument.exists?(url: url) })   # → [Payload(url, content_type, body)]
```

**仕事の分け方**: 「取得元が変わっても同じか？」で分ける。同じなら PoliteHttpClient、取得元ごとに違うなら Fetcher。

| 仕事 | 担当 | 理由 |
|---|---|---|
| User-Agent を付ける | PoliteHttpClient | リクエストそのものの共通部分 |
| 5秒間隔をあける | PoliteHttpClient | sitemap と詳細ページの間も含め、どのリクエストにも必要。Fetcher に書くと取得元を増やすたびに書くことになり、書き忘れが即ルール違反になる。「最後にリクエストした時刻」の状態もここが持つ |
| リダイレクトを追わない（3xx は失敗） | PoliteHttpClient | HTTP のレベルの決まりで、取得元に関係なく同じにしたい |
| sitemap を `lastmod` の新しい順に並べる | PaizaFetcher | paiza 固有 |
| 取得済みの URL を飛ばす | PaizaFetcher | `skip:` で受け取るので、Fetcher は DB を知らずに済む |
| 決めた件数で止める | PaizaFetcher | 件数そのもの（1日30件）は Runner から `limit:` で渡す（下記） |

- **テストで5秒待たない**: 待つ処理を `sleeper:` で外から渡す（依存性の注入）。本番は `->(s) { sleep(s) }`、テストは呼ばれた秒数を記録するだけのものを渡し、「待つ処理を呼んだこと」を確かめる。`sleep` をテストの中でスタブすると、テスト対象の中身に依存する（`RSpec/SubjectStub`）
- **途中で失敗したとき**: 失敗の影響が届く範囲で分ける

  | 失敗 | 影響の範囲 | 扱い |
  |---|---|---|
  | sitemap が取れない | 全体（どの URL を取るか決まらない） | すぐ中断 |
  | 詳細ページ1件が 404 / タイムアウト | その1件だけ | 飛ばして続ける。原文を保存しないので、翌日に自然に取り直される |
  | 403 / 429 | サイトが「やめてほしい」と言っている合図 | すぐ全体を中断する（拒否されたら回避しない） |

**「1日30件」の方針と、止める処理の実装を分ける**
- 方針（30という値）は全取得元で共通なので、最初から1か所に置く。PaizaFetcher には書かず、Runner から `limit:` で渡す。値が重複すると、直し忘れがそのままルール違反になる
- 止める処理（ループ）は、今は PaizaFetcher に書く。共通化は2つ目の取得元を作るときに、実物を見て判断する（いつ別のサイトを取るかわからないため）
- 共通化の案（2026-10-30 に検討、今は採らない）

  | 案 | 形 | 良い点 | 弱い点 |
  |---|---|---|---|
  | A. Fetcher は「候補の URL を優先順に並べる」だけにし、取得済みを飛ばす・件数で止める・1件ずつ取る・失敗を扱う、を Runner に寄せる | `PaizaFetcher#candidate_urls` → Runner が skip と limit を適用して取得 | 共通部分が Runner に集まり、Fetcher がとても小さくなる | API の取得元に合わない（Greenhouse は1回のリクエストで本文ごと全件返る） |
  | B. 今の形（`fetch_new(limit:, skip:)` が原文の配列を返す）のまま、2つ目の取得元を作るときに共通部分を抜き出す | 今は PaizaFetcher に素直に書く | 取得元ごとの取り方の違い（sitemap＋1件ずつ、API で一括）を吸収できる | 2つ目を作るまでは、共通にできる部分も PaizaFetcher の中にある |

  「2つ目で気づき、3つ目で抜き出す」。1つしか例がないと、共通と固有の線を推測で引くことになる。今は B

### DBスキーマ
```
raw_documents  id, source, url[unique], content_type, body, fetched_at, parse_error(NULL可)
jobs           id, raw_document_id[FK, unique], title, company, position,
               job_types(JSON配列), description, salary_min, salary_max,
               technologies(JSON配列), features(JSON配列), extracted_at
reactions      id, job_id[FK, unique], verdict(1 / -1), created_at
reasons        id, reaction_id[FK], aspect(tech_stack / description / salary / position), comment(NULL可)
```

| 判断 | 理由 |
|---|---|
| `url` にunique制約 | 取得済み判定がインデックスで済む。DB側でも重複を防ぐ |
| 原文1件 ＝ 求人1件（1対1） | paizaは詳細ページ1枚が求人1件。将来、一括で返すAPIを足すときも1件ずつ保存して流れをそろえる |
| 給料は下限・上限の整数（万円） | 範囲での絞り込みや平均ができる。「応相談」はNULL |
| `position`（職種名）と `job_types`（職種）を分ける | 1つの文字列にまとめると数えられない。職種名は企業ごとに自由な書き方なので表示用、職種はpaizaが決めた選択肢なので表記ゆれがなく集計に使える |
| ポジション・応募要件は持たない | 「見開きでパッと見て判断できる」ように情報は絞る。原文に残っているので、分析で必要になったらカラムを足して再抽出すれば過去分も埋まる |
| 技術・働き方は `jobs` のJSON配列 | 集計対象は評価済みの求人で、件数はスワイプの速さで決まる（多くても数百〜数千件）ため、Rubyで数えれば十分。表記ゆれは目で見てわかる |
| `features` を持つ（名前はpaizaの「特徴」に合わせる） | 中身は働き方（副業OK等）が中心だが、選考（オンライン面談可）・対象者（若手歓迎）・会社（社長が元エンジニア）も混ざるため、`work_styles` ではなく中身どおりの名前にした。成功の形2の「-1の理由に繰り返し出る避けたい働き方」の集計に使う。後回しにしていた働き方タグはこれで置き換える |
| parseの状態は `parse_error` だけで表す | 成功＝対応するjobsがある、失敗＝parse_errorあり、未parse＝どちらもない、と他のデータから導けるので状態カラムは作らない |
| `source` は文字列カラム | 取得元はコード（Fetcher / Parserのクラス）で決まり、それ自体に属性がない。2つ目の取得元を足すときのために最初から持つ |
| 評価は1求人につき1つ（`job_id` unique） | 興味の変化は、別々の求人を時期ごとに評価すれば評価日時で見える。履歴にすると「求人ごとに最新の評価だけ取り出す」集計が必要になり複雑 |
| `verdict` は 1 / -1 | 0 は「どちらでもない」と紛らわしい。`SUM` で好き − 嫌いが出る。Railsでは `enum :verdict, { good: 1, bad: -1 }` |
| 理由は別テーブル | 1つの評価に理由が複数付く。良い理由か悪い理由かは `verdict` から導けるので持たない |

### 反応の記録
- 評価は **+1 / -1 の2択**。迷ったら直感で決める（直感の反応こそ「思っている興味とのズレ」を示すデータになる）
- **0 は作らない**。「どちらでもない」に逃げてデータが偏るのを防ぐ
- 判断できない求人は **スキップ**（`reactions` に行を作らない）。未評価のまま残り、後でまた候補に出る
- 理由は自由文ではなく **質問形式** で答える
  - +1 のとき「何が良かったですか？」、-1 のとき「何が合わなかったですか？」
  - 選択肢: 技術スタック / 業務内容 / 給料 / ポジション（＋任意で一言）
  - 自由文のままでは数えられない業務内容やポジションも、「どの観点が効いたか」は数えられる。文字列そのものは求人側にあり、データが揃ったらAIなどで分析する
- 求人カードに出す項目（ぱっと見で「お！」となるもの）: 技術スタック / 業務内容 / 給料 / ポジション。4つとも集計に使う
- 求人情報の不備（情報が薄いなど）は、好みの評価とは別の問題として扱う（必要になったら求人側にフラグを付ける）

### 学習方針
学びたい順: **1. テスト → 2. デザインパターン → 3. DBスキーマ設計 → 4. 集計・検索ロジック（データ構造とアルゴリズム）**

| 強度 | 領域 | 進め方 |
|---|---|---|
| 強 | テスト（テストケースの設計） | 自分が先にケースを考える。AIは答えを出さず観点で問い返す（観点 → 具体例 → 答えの順） |
| 中 | デザインパターン | AIが案を出す前に自分が一言予測し、その後で比較する。必然性のないパターンは使わない |
| 軽 | DBスキーマ設計 / 集計・検索ロジック | AIが案を出してよい。理由を添え、承認してから実装 |

- 根拠: Anthropicの研究（2026-01）で、AIにコードを書かせるより、自分で考えてから確認する使い方の方が理解度が高かった https://www.anthropic.com/research/AI-assistance-coding-skills
- Claude Codeの出力スタイルは **Learning** を使う
- 認証 / Hotwire(Turbo) / デプロイ もアプリには取り入れる。ただし学習の優先順位は高くない（上表の対象外＝AIが通常どおり実装してよい）

### テスト
- RSpec を使う
- 書き方は Better Specs（https://www.betterspecs.org/）に従う。古い記述（have(n).items、Spork/Zeus、Guardの設定例）は採用しない
- rubocop-rspec を導入（デフォルト設定から開始）。ルールの無効化・緩和は理由を残して行う
- 外部HTTPは WebMock でスタブする
- テストケースを考える観点: 同値分割 / 境界値 / 異常系（空・不正値・欠損） / 外部依存の失敗 / 状態遷移

### 期間
- 1〜2週間。「動いた」で閉じる

## Walking skeleton（最初に作る範囲）
骨組みだけでいいので、最初から最後まで一通り動かす。各段階を作り込むのはその後。

```
保存済みサンプルを読む → 原文を保存 → parseしてjobsへ → カードで1件表示 → +1 / -1 / スキップ → +1一覧（B）
```

1. 入力は `samples/paiza/` のページ全体のHTML（ネットワークにつながない。テストのフィクスチャにも使う）。`paiza_lib/paiza/` の20件は一部分しかないので使わない
2. 骨組みが通ったら、paizaから実際に取得する部分（`PaizaFetcher`）を足す
3. その後、D（時期で絞り込む）→ A（グラフ・表）の順で太らせる

## 未決の論点
1. どのテストを厚くするか（model / request / system の配分）: 最初の機能設計時に決める
2. 原文の保存先と容量: paizaはページ全体で1ページ約65KBなので、1日30件で約700MB/年。gzipで圧縮するか、Active Storage（S3など）に移すかを、デプロイ先とあわせて決める
3. 分野タグ（14章の10分類: コンシューマ向け / エンタープライズ / データ集約型 / インフラ・DevOps / ゲーム / 教育 / 医療 / EC / モバイル / AI・機械学習）: walking skeletonの後で追加する（働き方タグはpaizaの「特徴」で置き換えた）
4. 2つ目の取得元（候補は [docs/job-sources.md](job-sources.md)）。そのときにStrategyを導入する
5. 理由の質問の選択肢（`reasons.aspect`）に「働き方」を足すか
